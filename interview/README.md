# 把 Frame 经历讲成能经得起追问的项目案例

[技术博客](../articles/README.md) · [学习课程](../beginner/README.md) · [贡献线索](../evidence/contribution-history.md)

作者确认自 2026-08-14 起负责相框的主要模块，涵盖 Portrait、Moment、Wi-Fi 和更新。面试时可以围绕这份负责范围讲自己的设计、实现和问题排查；具体案例中的发现过程、协作分工和验证结果，应采用自己实际经历过的事实。

## 先准备一个主案例

第一轮介绍不必把四个模块全部讲完。选一个能画流程、能解释失败、能指出代码的主题，其他模块作为追问时的补充。

| 想重点展示 | 主案例 | 面试官可能追问 |
| --- | --- | --- |
| Flutter / 媒体工程能力 | [Portrait](../articles/portrait-lifecycle-identity.md) | key 一样为什么还会重建资源？首帧与 playing 有何区别？ |
| 数据与播放状态设计 | [Moment](../articles/moment-cache-continuity.md) | 缓存完成为什么不能重置播放？暂停是否保留剩余时间？ |
| 平台协作与异步判断 | [Wi-Fi](../articles/wifi-readiness-handoff.md) | health 成功后掉线怎么办？timeout 有没有取消请求？ |
| 失败恢复与一致性 | [更新](../articles/app-update-recovery.md) | 已提交但回执未知怎么办？Retry 为什么不能无脑重做？ |

## 三档讲述长度

**30 秒项目介绍**：说清产品、主要负责范围和最突出的难点。可从下面这段改起：

> 我负责一个基于 Flutter 的 Android 智能相框项目，主要做 Portrait 动态展示、Moment 轮播、Wi-Fi 接入与 App 更新。项目里比较难的是持续播放、异步任务和 Android 系统状态之间的协调，比如缓存准备好了不能随便重启播放器，安装提交后也不能把未知结果当成失败直接重试。

**两三分钟主案例**：选择一篇文章末尾的讲述主线，按下面顺序讲，不要求机械使用每个标题：

1. 用户要完成什么动作，产品有什么约束。
2. 普通写法为什么会出错，给一个具体事件顺序。
3. 你把状态交给谁管理、在哪些时机检查身份或保存记录。
4. 方案保护了什么，还有哪些代价和限制。
5. 用了哪些反例验证；实际做过的设备验证再单独补充。

**十分钟深入**：画一张图，沿一个失败分支走到恢复。面试官问到别的模块时再切换，避免把所有接口名一起列出来。

## 一张个人案例卡

下面空白用于补自己的经历，不要把示例事故、建议实验或历史测试存在自动填成自己当时的事实。

| 要补的内容 | 写法提示 |
| --- | --- |
| 我具体负责什么 | 写设计/实现/排查/验证的实际范围和协作边界 |
| 用户能看到的问题 | 用“点击后发生什么”描述，别只写“优化体验” |
| 最初方案 | 说清它在哪个约束下不够用 |
| 我怎么定位 | 日志、状态回读、最小复现或代码追踪中真实用过的办法 |
| 关键改动 | 状态归属、身份比较、提交顺序、资源释放中最重要的一两处 |
| 如何验证 | 具体输入、事件顺序和断言；设备结果单独写 |
| 可证明的结果 | 可复述的行为改变；有一致条件测量时才写量化收益 |
| 再做一次会改什么 | 现有方案的明确边界与可行改进 |

提交可以帮你找回细节。先用[精选提交](../evidence/contribution-history.md)定位改动，再想起当时的现象；一个整合提交不必只对应一个人的一项任务，也不自动等于一次完整上线。

## 简历表述草稿

以下是基于负责范围与技术实现的候选句。按真实经历选择两三项，避免全部挤进一段，也不要在没有证据时添加“提升 80%”“零故障”等结果。

- 负责 Flutter Android 相框核心功能开发，覆盖动态宠物展示、媒体轮播、Wi-Fi 接入和 App 更新，并处理页面、异步任务与平台资源的生命周期协调。
- 在 Portrait / Moment 播放链中区分业务内容身份与媒体来源变化，使用结果归属检查和连续性策略，处理快速切换及网络到本地缓存升级场景。
- 设计 Wi-Fi 的分阶段就绪判断和操作轮次失效机制，分离平台连接、业务服务检查与页面导航，并处理迟到回包及状态读取超时。
- 实现 App 更新的持久化尝试与恢复流程，区分安装准备失败、提交结果未知及事件回报重试，保留可审查的恢复入口。

“负责”与“设计”的具体范围由作者经历确认。若某一项主要是维护或排查，改成“维护”“参与实现”“定位并修复”会更准确；不要因为文章解释了整条链，就默认每个底层库都由自己原创。

## 判断自己是否已经能拿去面试

合上文章，试着回答：

- 能否不用类名，先解释用户遇到的问题？
- 能否画出两次异步请求交错的顺序，而不是只说“用了锁/状态机”？
- 能否删掉一个保护条件，指出具体错误结果？
- 能否说出一种替代方案，以及自己方案的代价？
- 能否区分“代码这样写”“测试这样断言”和“设备实际看到这样运行”？

卡在前两条就回文章的小例子；卡在实现细节就按来源索引打开一个函数；卡在结果就补自己的验证记录。一次练熟一个案例，比记住四篇的全部术语更有用。

需要模拟面试时，可以这样问：

> 我准备讲 Frame 的 Portrait 案例。先听我的两分钟介绍，再依次追问身份、异步竞争、资源生命周期和验证。一次只问一个问题，根据我的回答继续，不替我编经历；指出我应该回看文章的哪一段。
