# 13 从节日音乐理解路由可见性与媒体所有权

[课程入口](README.md) · [本期来源](../evidence/app-october-source-map.md#audio) · [上一期](12-popup-scheduling.md)

阅读快照：2026-10-26。案例来自 10 月 21 日至 26 日节日音乐、视频声音接管和按展示场景选曲的演进。本期学习：媒体资源存在、页面还活着、用户应该听到声音，是三个不同条件。

先修：[生命周期](../beginner/06-lifecycle.md)、第 10 期异步资格。核心问题：**关闭一个视频时，为什么不能直接调用背景音乐 play？**

## 将选曲与播放许可分开

当前业务规则要求日常音乐为默认，节日曲目只由明确的节日展示场景启用。曲目已缓存不代表当前页面符合场景，活动时间有效也不意味着登录、建宠或普通宠物空间应播放节日曲。

| 维度 | 例子 | 决定什么 |
| --- | --- | --- |
| 资源 | 音频是否可用 | 有无可装载的曲目 |
| 排期 | 已确认的活动时间窗口 | 节日选曲是否可能生效 |
| 场景 | 当前可见的活动页或节日原图 | 当前内容是否明确选择节日音乐 |
| 播放许可 | 前台、声音设置、启动门禁、音频中断 | 此刻能否播放 |
| 媒体占用 | 视频或其他前景播放 owner | 背景音乐是否必须让位 |

Controller 先根据场景选目标资源，再在播放前复查许可。表格只是职责分解，未穷尽项目中的全部条件；不能把它直接当成完整的播放授权函数。

## mounted 不能回答页面是否可见

一个新页面 push 上来，下面页面的 State 可能仍然 mounted。底层 Home 如果继续声明节日场景，就可能把普通页面的音乐带偏。

`BackgroundMusicScene` 使用 `RouteAware`：覆盖时撤下场景，返回时恢复声明；路由订阅首次回调也要结合 `route.isCurrent` 判断。页内 tab、阅读和浮层还需业务方提供实际展示状态，路由名 `/home` 本身不足以表达当前内容。[RouteAware 官方说明](https://api.flutter.dev/flutter/widgets/RouteAware-class.html)

临时对话框通常继承宿主场景，但完整的普通内容即便实现为 `PopupRoute`，仍可能需要显式普通场景覆盖。因此路由类型只是输入，实际展示语义才决定策略。

## 为什么用 owner 集合管理暂停

假设视频 A 和媒体 B 都要求背景音乐暂停：

| 事件 | 暂停 owner 集合 | 能否仅因本事件恢复 |
| --- | --- | --- |
| A 开始 | `{A}` | 否 |
| B 开始 | `{A, B}` | 否 |
| A 结束 | `{B}` | 否，B 仍占用 |
| B 结束 | `{}` | 可重新评估，仍要看前台与静音等条件 |

一个共享 bool 无法表达两位持有者；A 设置 false 就会错误解除 B 的暂停。集合还让重复释放 A 成为无效操作，不会多减一次计数。

下面是完整教学类，只管理占用身份，不执行播放，也不等同于项目 Controller：

```dart
class MediaOwners {
  final Set<Object> _active = {};

  void acquire(Object owner) => _active.add(owner);
  void release(Object owner) => _active.remove(owner);
  bool get blocksBackground => _active.isNotEmpty;
}
```

owner 必须稳定地代表一次独立生命周期。若 acquire 和 release 各自创建一个新 `Object()`，释放不到原持有者；若不同媒体错误共用一个 owner，也会失去隔离。布尔型占用和需要嵌套次数的引用计数不可混用。

项目中，活动 Start 后的动作等待、三段播放、结果与页内重播连续持有背景暂停权。不能见视频暂时不在播放就恢复背景声，否则段间等待和结果页会出现意外混音。

## 异步换曲也会发生乱序

目标曲目从日常变为节日时，原生 load 仍可能未完成；用户又切回普通页面。如果 load 返回后直接 play，就会播出已经过时的目标。

当前 `_syncResource` 在串行任务内装载，并在异步返回后比较最新目标；`_playIfAllowed` 在激活 audio session 后再次检查许可。页面场景交接还按帧合并，避免两个节日页互相切换时短暂装载日常曲目。同曲不重载和撤销旧播放资格，分别解决无意义切换与迟到执行。

串行化保证调用顺序，但不冻结业务条件。队列执行到这一项时仍须检查最新场景与 owner，不能认为“已经排进队列”就是永久播放许可。

## 最少源码阅读顺序

1. `background_music_scene.dart`：看 `_visible`、`didPushNext`、`didPopNext` 和 `dispose`。
2. `background_music_controller.dart`：看场景集合、`setForegroundPlayback`、`setHalloweenPlayback`。
3. 只继续到 `_syncResource`、`_playIfAllowed`，画出两处等待后复查。

停止点：能跟完“活动页 → 普通页 → 返回 → 视频开始 → 退出”的时间线；原生音频焦点与实际听感另需设备验证。

## 预测题与反例

A 退出后集合为空，但用户已把 App 静音，是否应该恢复音乐？

<details>
<summary>展开答案与理由</summary>

不应该。释放暂停权只解除一个条件，不能覆盖静音、后台或系统中断。应调用统一的重新评估路径，由它决定是否播放。

</details>

节日页被新页面盖住但未 dispose，仅在 dispose 中清理场景会怎样？

<details>
<summary>展开答案与理由</summary>

旧场景会继续影响当前曲目。需要路由可见性事件和页内展示状态，不只依赖对象销毁。返回时也要依据当时排期和资源重新评估，而非盲目恢复进入前的曲目。

</details>

## 练习与完成标准

运行[媒体 owner 实验](../labs/app-october/README.md)：依次取得 A、B，释放 A 两次，再释放 B。观察只有集合完全为空时才解除占用；实验没有真实音频输出。

再纸面增加“B 持有时进入后台，随后 B 释放”这一分支。完成标准：能分别说明资源准备、场景选择、播放门禁和所有权释放，并为每个 owner 找到对称的取得与清理位置。它可迁移到摄像头、麦克风、屏幕常亮和其他共享原生资源。
