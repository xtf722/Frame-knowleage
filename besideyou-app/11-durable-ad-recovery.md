# 11 从广告中断恢复理解持久命令与幂等

[课程入口](README.md) · [本期来源](../evidence/app-october-source-map.md#recovery) · [上一期](10-async-identity-and-cache.md) · [下一期](12-popup-scheduling.md)

阅读快照：2026-10-26。案例来自 10 月 23 日至 25 日 Gem 广告冷启动恢复、原次重试及账号隔离。本期学习：当进程可能随时消失，内存中的 `try/catch` 不足以保证业务连续。

先修：第 10 期异步归属，以及 [Future](../beginner/03-future-await.md)。核心问题：**请求结果丢了，再试一次究竟是恢复原操作，还是创建第二笔操作？**

## 一次超时有两种不同的世界

世界 A：请求没有到服务端。世界 B：服务端已经记账，但响应在途中丢失。客户端看到的都可能是超时。

如果失败后创建新 key，世界 B 就可能产生第二笔业务。幂等 key 表达“这是同一项业务意图”；恢复时保留原 key 和原尝试 ID，让服务端识别原请求。真正的幂等处理必须由服务端实现，客户端按钮禁用和本地记录都不能替代它。

## 先落盘再跨越不可回退的边界

| 顺序 | 保存或执行什么 | 解决的崩溃窗口 |
| --- | --- | --- |
| 1 | 保存原幂等 key | 创建请求已提交但 ID 尚未返回 |
| 2 | 接到响应后保存原 attempt ID | 后续核对能定位同一次尝试 |
| 3 | 调用 SDK show 前保存 `display_started` | 原生展示可能发生，但 Dart 没等到回调 |
| 4 | 收到奖励回调立即保存 `verification_started` | 已观察完成，却在关闭广告前被杀进程 |
| 5 | 上报真实观察，再读取服务端状态与钱包 | 本地 SDK 事件不直接变成资产 |
| 6 | 服务端终态后清理原次记录 | 未决记录不会过早丢失 |

`display_started` 在 show **之前**写入，严格说代表“展示可能已开始”，不是一份证明用户确实看见广告的收据。先写后调用仍有两步之间崩溃的窗口；这正是重启后必须上报观察、由服务端决定恢复权限的原因。

SDK 回调是平台观察，服务端交易与钱包才是本案例的到账依据。收到回调就 `balance += 1` 会把重复事件、异常中断和服务端拒绝都混进资产状态。

## 核对奖励和重试加载是两个动作

本次代码支持在明确未完成的中断后恢复同一笔广告，但不是所有 pending 都能重播。

| 读取到的情况 | 允许的下一步 |
| --- | --- |
| 明确未展示，或明确开始后中断且没有完成记录 | 先保存并上报对应观察，再检查原次许可 |
| 原次 pending、服务端允许 retry、必要观察已成功上报 | 用户主动点击后按原 ID 获取凭证，加载后再核对 |
| 已观察奖励完成、主动取消、结果未知或无重试许可 | 只核对原次与钱包，不自行再次 show |
| 加载期间原次到账或许可撤销 | 采用新状态，不再展示 |
| 换号或旧会话失效 | 停止原异步续接，记录留在原账号分区 |

冷启动、恢复前台和钱包刷新不自动展示广告；只有用户动作才接续获准重试。GET 不提供播放凭证，opaque SSV token 不落盘、不记录到日志。期限到达也不能自行推定到账或重新延长原尝试。

## 存储队列为何不能只用一个 Map

`GemOperationStore` 按环境与账号隔离，串行执行“读现有状态 → 修改某项 → 写回”。否则两个异步调用都读到旧 Map，各自写回时可能覆盖对方的新记录。原生存储和 Web 内存替身的恢复能力不同，Web 内存不能证明杀进程后恢复。

队列还要区分两条 Future：返回给调用者的那条必须保留失败；供下一项排队的尾部需要收敛错误，避免一次失败永久阻塞后续任务。不能把调用者应看到的错误一起吞掉。

教学片段，`tail` 是外部定义的 `Future<void>`，`action` 由调用者提供；不包含实际磁盘存储：

```dart
Future<T> serial<T>(Future<T> Function() action) {
  final result = tail.then((_) => action());
  tail = result.then<void>((_) {}, onError: (Object e, StackTrace s) {});
  return result;
}
```

`result` 仍会把失败交回当前调用者；`tail` 只让下一次排队可以继续。该技巧保障执行顺序，不自动提供数据库事务或跨进程锁。[Dart 异步基础](https://dart.dev/libraries/async/async-await)

## 预测题与反例

服务端已成功，但客户端没收到响应。用户点重试时换一个新 key，为什么本地禁止双击也救不了？

<details>
<summary>展开答案与理由</summary>

禁止双击只减少同一时刻的重复调用；隔几秒或重启后仍可以创建第二笔。恢复必须保持业务身份，服务端也必须按该身份去重。见离线实验的 `--broken-key`，它故意换键，导致模拟服务端执行两笔。

</details>

磁盘记录损坏时，将其当作“没有未决任务”并创建新广告是否合理？

<details>
<summary>展开答案与理由</summary>

不合理。损坏表示无法确认旧任务，不表示旧任务不存在。应保留问题并关闭新增动作，允许独立查询钱包；不能用清空记录掩盖未知结果。项目的存储解析失败沿错误路径传播。

</details>

## 练习与完成标准

运行[恢复实验](../labs/app-october/README.md)：模拟服务端已经执行但响应丢失，重建客户端对象后用原 key 再发，观察服务端仍只有一笔。实验的“磁盘”和“服务端”都是进程内替身，只验证协议思想，不验证真实磁盘原子性或真实杀进程。

再手写三个崩溃点：ID 返回前、show 之前、奖励回调之后。为每一点填“已有记录、未知事实、允许动作”。完成标准是能解释原键恢复、权限复核和权威记账的各自责任，可迁移到提交订单、报名、上传确认及内容消费。
